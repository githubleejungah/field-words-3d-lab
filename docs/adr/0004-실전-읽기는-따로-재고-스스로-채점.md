# ADR-0004: 실전 읽기 확인은 게임 기록과 따로, 실행 없이 글로 적고 스스로 채점한다

- 상태(Status): **채택(Accepted)** — 2026-11-23 설계 문서와 함께 사용자 승인
- 날짜: 2026-11-23
- 결정한 사람: 프로젝트 오너(사용자)가 방향을 정함(요구 Q28). Claude가 구조를 제안.

## 1. 배경 (Context)

- 게임은 사람이 고른 짧은 예제(3~10줄)를 도움을 받으며 읽는 힘을 기른다. 그러나 이것이 실무 코드를 읽는 힘으로 이어지는지는 따로 재야 한다(Q28).
- 사용자 프로젝트(리테일 챗봇) 코드는 민감 정보만 빼면 공개해도 된다(Q28 답). 저장소는 비공개다.
- 비용 0원, LLM 호출 0개(AC-01 · 02). 학습 기록은 밖으로 보내지 않는다(AC-03).

## 2. 선택지 (Options)

| 방법 | 실무와 같은가 | 0원 · LLM 없음 | 판단 |
|---|---|---|---|
| 게임 ② 형식(보기 4개)으로 실제 코드 | ❌ 보기가 힌트가 된다. 실무에는 보기가 없다 | ○ | ❌ |
| 실제 코드를 실행해 결과 맞히기 | △ | ❌ Vue · 서버 코드는 브라우저에서 혼자 돌지 않고, 사람이 고른 예제만 실행한다는 원칙(AC-04)과 어긋남 | ❌ |
| AI가 내 설명을 채점 | ○ | ❌ LLM 호출(AC-02) · 비용 | ❌ |
| 3D 장면으로 보여 주기 | ❌ 실무에 없는 도움이라 재는 대상이 달라진다(Q24) | ○ | ❌ |
| **도움 없이 읽고 3칸에 글로 적은 뒤, 모범 답 · 꼭 짚을 점과 비교해 스스로 채점** | ○ 실무에서 남의 코드를 읽고 설명하는 일과 같다 | ○ | ✅ 채택 |

## 3. 결정 (Decision)

1. 실전 읽기는 문제 데이터와 다른 파일(`site/data/reading.json`), 다른 기록 키(`cm:v1:reading`)에 둔다.
2. 처음 1번(기준값)과 그 뒤 28일마다 처음 화면 카드로 권한다. 막지는 않는다.
3. 코드 20~30줄을 줄 번호와 함께, 실행 없이, 도움 0개로 보여 준다.
4. 3칸(무엇 · 입력과 결과 · 가장 중요한 줄과 이유)에 글로 적고, 모범 답과 꼭 짚을 점 3~5개를 보고 점마다 맞힘 · 부분 · 놓침을 고른다.
5. 점수 = (맞힘 1 + 부분 0.5) ÷ 점 수. 회차마다 1개 값으로 남긴다. 복습 상자 · 하루 단계 · 등급에는 쓰지 않는다.
6. 코드는 사용자가 비밀 값이 없는지 본 뒤, 검사 도구의 비밀 값 모양 검사를 지나야 커밋한다.

## 4. 결과 (Consequences)

- 좋은 점: 게임 밖 실력을 0원으로 잴 수 있다. 학습 기록과 섞이지 않아 승급 · 복습 계산이 흔들리지 않는다.
- 나쁜 점: 스스로 채점이라 후하게 줄 수 있다. → 꼭 짚을 점에 사실 하나씩만 써서 가리기 쉽게 한다.
- 나쁜 점: 회차마다 코드가 달라 난이도 차이가 점수에 섞인다. → 같은 코드를 다시 읽은 회차는 "다시 읽음"으로 표시한다. 코드 수는 시제품 뒤 다시 본다(AS-13).
- 나쁜 점: 비밀 값 모양 검사는 모든 비밀을 잡지 못한다. → 사람 확인을 첫 관문으로 둔다.
