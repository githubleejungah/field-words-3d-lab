# 요구 — 필드워드 코드 해석 게임 ("코드 가려 보기")

- 상태: **인터뷰 진행 중** (2026-11-21 시작). 3~5(아키텍처 · 데이터 · 흐름) 문서는 이 문서 확인 뒤에 쓴다.
- 위치: 필드워드 저장소 **밖** 시제품 폴더. 필드워드 데이터 반영은 사용자의 다른 계정이 하므로, 여기서는 필드워드 저장소를 고치지 않는다. 시제품은 공개된 `glossary.json`을 읽기만 한다.

## 1. 원문 (사용자 기획 문장, 고치지 않음)

> 지금 필드워드의 방식 유지하면서 개발용어를 3D로 쉽게 해석할 수 있는 게임같은 앱기능을 붙일 수 있는지 확인해주세요. (2026-11-21)

> 그럼 필드워드에 넣을 가상 게임화가 가능한지 논의는 여기서 진행해도 될까요? 그건 필드워드에서도 진행하지 않았는데 강의 들으면서 3D를 클로드씨가 만들 수 있다는 걸 알았거든요. (2026-11-21)

> 클로드씨가 프로그램 용어를 잘 해석하기 위해서는 내가 만든 프로그램을 어디를 가려보고 실제 어떻게 변하는지를 찾아 보라고 했어요. MARK 를 말할 때 같이 예로 들어줬던 거 기억나세요? 그것이 가능하려면 어떤 게임 형태가 좋을까요? (2026-11-21, Q1 답)

> MASK 맞아요. 제가 잘 못 기억했어요. 그리고 게임 내용을 잘 이해하지 못했어요. 그리고 제가 12월 2일까지 AZER 무료가 있는데 속도를 위해 개발은 AZER 에서 하고 서비스는 기존 필드워드에서 하면 컴퓨터 부하가 덜 할까요? 이 방법이 가능할까요? 그리고 프로그램언어를 잘 해석하는 게 목적인데 클로드씨가 말해준 게임 방법이 인간의 인지행동학에 근거로 봤을 때 잘 이해가 될까요? (2026-11-21)

> 아...혹시 이건 챗봇 설계 공부노트와 더 유사한 거 아닌가 싶은데요. 제가 생각한 건 정말 코딩을 해석하는 게임이예요 (2026-11-21)

> 오! 그런데 먼저 저 문제를 내기 전에 해석이 먼저 돼야 하지 않을까요? 이건 반영하라는 게 아니라 클로드씨와 상의하는 거예요 (2026-11-21)

> 그것까지 생각하지는 않았는데 단계 너무 좋아요. 그리고 3번이라면, 글자 입력보다 필드워드처럼 보기로 누르는 게 어떨까요? (2026-11-21)

> 오! 좋아요. 이걸 현재 필드워드 처럼 무료로 배포하는 방식을 유지할 수 있어요? 사용자도 저도 비용이 따로 들지 않아야 해서요. (2026-11-21)

## 2. 인터뷰 (Q/A)

| # | 질문 | 보기 · 추천 | 답 |
|---|---|---|---|
| Q1 | 가장 먼저 만들어 볼 게임은? | 헷갈리는 짝 분류(추천) · 9단계 현장 지도 · 요청 여행 | 원문 3번째 문장. "내 프로그램의 한 부분을 가리고 실제로 어떻게 바뀌는지 보는" 형태를 원함 → 가려 보기(어블레이션) 방향. "MARK"는 사용자가 **MASK(가리기)**가 맞다고 확인 |
| Q1-1 | (사용자 질문) 개발은 Azure, 서비스는 필드워드(GitHub Pages)로 하면 PC 부하가 줄까? | 답: 게임은 보는 사람 브라우저에서 그려지므로 개발 위치와 무관. 개발 작업 자체가 가벼워 Azure 불필요(로컬 개발 추천). 서비스는 GitHub Pages 그대로 가능 | 사용자 판단 대기 |
| Q1-2 | (사용자 질문) 이 게임 방식이 인지과학 근거로 이해에 도움이 되나? | 답: 예측 → 실행 → 관찰 → 설명 구조는 근거가 있다(PRIMM, 사전 시험 효과, 과잉 교정 효과, 개입으로 인과 배우기). 단 3D 장식은 오히려 방해(유혹적 세부 효과) | — |
| Q2 | 게임 무대로 쓸 프로그램은? | 리테일 챗봇(추천) · 필드워드 자체 | 방향 수정: 구조(부품) 가리기는 공부노트와 비슷하다. **코드 자체를 해석하는 게임**을 원함 → 코드 한 줄 · 단어를 가리고 실제 실행 결과 변화를 보는 **코드 가려 보기**로 전환. 구조 게임은 버림 |
| Q3 | 처음 다룰 프로그래밍 언어는? | 자바스크립트(추천: 브라우저에서 바로 실행) · 파이썬(Pyodide 약 10MB) · 둘 다 | (대기) |
| Q4 | (사용자 질문) 문제를 내기 전에 해석이 먼저여야 하지 않나? | 답: 처음 보는 코드는 해석 먼저(풀이 예제 효과), 한 번 본 코드는 예측 먼저(사전 시험 · 과잉 교정, 전문성 역전 효과). → **3단계 사다리**: ① 해석 보기 ② 가려 보기 ③ 해석 고르기. 학습자 상태(모름 · 헷갈림 · 앎 · 착각)로 시작 단계를 정한다 | "단계 너무 좋아요" — 채택 |
| Q5 | (사용자 제안) ③은 글자 입력보다 필드워드처럼 보기로 누르면? | 답: 보기 방식이 맞다(한 손 · 이동 중, 서버 없이 채점, 착각 보기로 오개념 진단). 생성 효과를 지키려고 **떠올린 뒤 보기 열기**. 글로 쓰기는 선택 기능 | 채택 |
| Q6 | (사용자 질문) 필드워드처럼 무료 배포를 유지할 수 있나? 사용자도 나도 비용 0원 | 답: 가능. 정적 파일 + GitHub Pages, 실행 · 채점 · 기록 모두 브라우저 안. 비용이 생기는 기능(LLM 채점 · 힌트, 로그인 · 동기화, 클라우드 서버)은 넣지 않는다 | 비용 상한 **0원** 확정 |
